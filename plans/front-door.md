## 段1の設計の芯（2026-11-11。§1 の案を、コードを読んで詰めたもの）

### 素材の置き方: 中身の SHA-256 を名前にして、1つの Release に置く

- 公開用リポジトリに Release を1つ（タグ `site-media`）。資産の名前は `<SHA-256>.<拡張子>`（例 `1ccb…2885.mp4`）
  - 名前が中身で決まるので、上書きが起きない（古い版の素材も消えない＝仕様 §1「版は増えるだけ」がそのまま守れる）
  - ja と en で同じ絵・同じ曲は1つで済む（スムージーは絵の元・曲4本が同じ）
  - Release は置き場にすぎない。どれを使うかは目録が決める
- 台本（`work.json`・`script.md`）も同じく Release に置く（改行を LF にそろえて量る）。git の `examples/` には今の版しか無く、古い版を写せないため。
  一番新しい版の台本が `examples/` と同じことはテストで見る（`tests/scripts/sites.test.js`）

### 目録: `examples/<slug>/<lang>/site.json`（git に置く）

```json
{ "version": 1,
  "files": [ { "path": "pictures/_built/01.jpg", "size": 340192, "sha256": "…" },
             { "path": "videos/ending.mp4", "size": 21206892, "sha256": "…" } ],
  "levels": { "sounds/bgm.mp3": -31.2 },
  "card": { "line": "小学生くらい・約6分・…" } }
```

- 載せるのは上演に要るファイルだけ（work.json が指す絵・音・動画）。下絵・`key_26.png` などは載せない
- `levels` は BGM の測った大きさ（LUFS）。語り手は曲を丸ごと読み解かずに済む

### 取り込み: `scripts/fetch-samples.mjs`（Node の標準だけ）

- 目録ごとに Release から取り、SHA-256 を確かめて `player/samples/<slug>/<lang>/<version>/…` に置く。合わなければ止まる（配らない）
- 台本は `examples/` から写す。見本の一覧 `player/sample-list.json`（slug・lang・version・題・1行）も作る
- 目録は版を積み上げる（`versions` の配列）。取り込みは全部の版を置く（サイトの版は増えるだけ）
- 目録と上げるファイルを作るのは `scripts/site_media.py`（ffmpeg。25 MiB を超える動画は 720p に作り直し、音は写す）
- 手元では取ったものを `.cache/site-media/` に残し、2回目は取らない。`player/samples/`・`player/sample-list.json`・`.cache/` は `.gitignore`
- 開発用の箱の「ビルドのコマンド」に入れる1行: `node scripts/fetch-samples.mjs`（できてから渡す）
- 公開用は `ci.yml` の deploy の `wrangler deploy` の前に同じ1行
- `_headers` に `/samples/*` の `Cache-Control: public, max-age=31536000, immutable`

### 語り手: `narrator.html?sample=<slug>`（言語はブラウザで。`&lang=` で替えられる）

- `sample-list.json` から版を引き、work.json を取り、素材を `fetch` して File にし、いまの `workMap` に入れる → `resolve()` 以下は変えない
- 最初の版は**全部を取り終えてから**準備ができたとする（スムージーで約38MB。進み具合を出す）。§1.3 の「絵と最初の BGM だけ先に」は、
  遅いと分かってから（作りが増えるので後回し）
- `measureLevels` は目録の `levels` があればそれを使う
- 取り終えたら、そのまま上演の画面の練習へ（いまの「Practice」と同じ）

### 聞き手: 音と動画をサイトから取る

- サイトの見本として開いたときだけ、welcome の `audio[]`・`videos[]` に `src`（`samples/…` のサイトの中の道）を付ける
- 聞き手は `src` があれば `fetch` して、いまの保存（`store.writeSegment`）に 4MB ずつ書き、`have` で「全部ある」と言う → 語り手からは送らない。
  取れなければ書かずに `have` を返す → いまの「語り手から送る」に戻る
- `src` は `samples/` で始まる同じサイトの道だけ受ける（聞き手が確かめる。CSP の `connect-src 'self'` もある）
- **絵は最初の版では今までどおり語り手から送る**（5枚で約1.5MB。中継の費用の大半は動画）
- データで確かめるテスト: フォルダから開いた作品の welcome に `src` が1つも無い

### 玄関

- いまの合言葉の欄の下に、`sample-list.json` から見本のカード（ブラウザの言語で）: 題・1行・「1台で通して見る」
- 「どんな感じ？（1分）」の動画と、受付を「家族の端末をつなぐ」に言い換えるのは、段1の後半

### 段1の中の順番

1. 目録・取り込みの道具・テスト → Release `site-media` に上げる（**公開用への書き込みなので持ち主が打つ**。コマンドは渡す）→ Workers Builds の1行
2. 語り手の `?sample=`
3. 聞き手がサイトから取る
4. 玄関のカード
5. ヘッドレスで通す（手元の http サーバーで。e2e は今と同じ作り）→ 開発用の箱 → 持ち主の実機（iPad を入れる）

## 段2の設計（2026-11-11。§3 の案を、コードを読んで詰めたもの）

### 替えられる単位: 「印の付いた行の連なり」

- 1枚の中で、同じ印（`~1 `）の行が続いている所を1つの欄にする（スムージーの4枚目のように、印の無い行のあとに `~1 ` の行が
  続く段落でも、替えられるのは印の付いた行だけ）。欄には印を見せない。改行はそのまま
- 欄を空にすると、その行は消える（その穴は語らない）。「見本の文に戻す」で戻せる
- 替えられるのは、サイトの見本を練習しているあいだだけ（家族の端末をつないだら閉じる）。フォルダから開いた作品はいまのまま（修正票）

### 変えた版の作り方（純粋な関数 `player/js/variant.js`）

- 元は見本のその版の `script.md`（サイトの版のフォルダにある）。欄の文を、行ごとに同じ印を付け直して差し替える。ほかの行は一字も変えない
- 見出しに `> Based on: <題> (<slug>/<lang>, version N) — Digital Kamishibai, by Fast Focus Technologies, CC BY 4.0, https://digitalkamishibai.org`
  と `> Changed: 穴1（1・4・5枚目）` を入れる（`> Language:` の次。前にあれば置き換える）
- 画面に出す作品は、見本の `work.json` の語り（notes）だけを、変えた版を B3 の芯（`readScript`）で読んだ notes に替えたもの。
  替える前に、枚の数・題・合図が見本と同じことを確かめる（違えば開かずに理由を出す）——焼いた絵・素材は見本のまま使える
- 語りは聞き手へ送らない（いまの保証のまま）。変えた版でも welcome に notes が入らないことをデータで確かめる

### 残し方

- ブラウザ（localStorage）に `dk-variant:<slug>:<lang>` で1つ（最初の版は見本と言語ごとに1つ。2つ目を残したくなったら足す）。修正票とは別の鍵
- 変えた直後に知らせを1つ: 「この端末のこのブラウザに置きました。ほかの端末で語るとき・消えて困るときは、ファイルに保存してください」＋「ファイルに保存」。
  保存は `script.md` そのもの（`<slug>-<lang>-script.md`）。`navigator.storage.persist()` はこのボタンのあとにだけ呼ぶ
- 開き直す: 玄関のカードに「変えた版で開く」（ブラウザに残っているときだけ）。準備の画面に「台本のファイルを開く（.md・.zip）」と「台本を貼る」
- 開き直したとき: `Based on` の版がサイトにあればその版の素材で開く（サイトの版は増えるだけ）。無ければ一番新しい版を、
  枚数と各枚の `[Picture]` の行が同じときだけ使い、そう知らせる（仕様 §6）

### zip（決定5: 読む・書くは段2で）

- 読む: `player/js/zip.js`。`DecompressionStream('deflate-raw')` で、ライブラリなし。中身は要るときに1つずつほどく
- 準備の画面の「台本のファイルを開く」で zip も受ける: 中に `work.json`（＋素材）があれば作品フォルダと同じに開く（iPad は
  フォルダを選べないので、これで自分の作品を開ける）。`script.md` だけなら変えた版として開く
- 書く: 無圧縮の zip（CRC32 だけ）を同じモジュールに作り、テストで守る。画面で使うのは段4（写真を添えるとき）。段2で残すのは script.md だけなので

### 段2の中の順番

1. `variant.js`（印の連なり・差し替え・見出し・Based on を読む）とテスト
2. 語り手の画面: 「語りを変えてみる」の欄・見本の文に戻す・その場で画面の語りが変わる
3. 残し方: ブラウザに残す・知らせ・ファイルに保存・persist
4. 開き直す: 玄関の「変えた版で開く」・準備の画面の「台本のファイルを開く／貼る」・版の扱い
5. `zip.js`（読む・書く）とテスト → 準備の画面で zip を開く
6. e2e（変える → 残る → 開き直す → 聞き手に語りが行かない）→ 開発用の箱 → 持ち主の実機（iPad を入れる）

## 段3の設計（2026-11-11）

- 場所: 語りを変える欄の中。番号の付いた穴の、その枚の最初の欄に「AI に相談」（手引きにその穴の節があるときだけ）
- プロンプト（`player/js/advise.js` の `buildPrompt`）: 穴1つ分。その穴がかかる枚の語りを「替える所」「変えない所」に分けて
  （いま欄に書いてある文を入れて）、手引き（holes.md）のその節、約束（語る文だけ・改行・`[Slide N]`・1つのコードブロック・
  替える所の数と順）。頭に「家族の名前や写真は渡さなくてかまいません」
- 語る人自身の話の穴は、手引きの節に「**自分の話を見つける問い**」（en: **Questions to help you find your story**）が
  あるかで見分け、AI に話を作らせず、問いを2〜3個、1つずつ聞かせる。スムージーの穴1に問いを3つ足した（火の穴1にはもとからある）
- 帰り道（`parseAnswer`）: コードブロックの中を `[Slide N]` で分け、その枚の替える所へ順に。替える所が1つの枚は段落をまとめる。
  数が合わない・この穴の無い枚・見出しが無い答えは、理由を出して入れない。開いていない枚の欄にも入れる（閉じたときに残す）
- 手引きをサイトに置く: `site_media.py` が holes.md も目録に載せる（スムージーは版3。変わったのは holes.md だけ）
- 実機で ChatGPT に通した（2026-11-11）: 問いを1つずつ3つ聞き、話を作らず、`[Slide N]` と替える所の数どおりに返した（欄にぴったり入る）。
  ただしコードブロックに入れず、見本の「／」「♩」を使わず、健康の効き目の話（検査値）が入った。約束に2行を足した:
  変えない所と同じ書き方（「／」「♩」）にそろえる・健康や病気への効き目は確かめていなければ言い切らず「〜と聞いた」の形に

## 段4a の設計（2026-11-11。持ち主の返事で決めた）

87ac334 の時点のコードを読んで書いた。段4a は「チャット AI が見本を元に書いた script.md を貼る（開く）と、見本の絵と素材で開く」。

### いまの道と、どこを広げるか

- いまの「台本を貼る／台本・zip のファイルを開く」（`narrator.js` の `openFromScript` → `openSample({script})` → `textsFrom`）は、
  `Based on` が無ければ「見本を変えた版ではありません」、黄色い所のほかが変われば「ここではまだ開けません」で止まる
- 広げ方: 開く台本を2つに分ける。**黄色い所のほかが見本と同じ → いまの段2の道（そのまま）**。違う → **段4a の道**（下）。
  段2の道は1字も変えない（欄・見本の文に戻す・AI に相談がそのまま使える）

### 段4a の道: 骨組みが見本と同じなら開く

- 読む: 貼った台本を `readScript` で読む。errors があれば今の符号つきの文で止まる（`[BGM after video]` などはビルダーへの案内）
- 骨組みを比べる（新しい純粋な関数 `variant.js` の `sameSkeleton(sampleRead, read)` → `{ ok }` か、枚ごとの理由の一覧）:
  - 枚の数が同じ
  - 各枚の `picture`（`[Picture]`）・`cues`（`[BGM…]`・`[Sound]`・`[Video]`）・`texts`（`[Text]`）が、見本を読んだものと同じ
  - ⚠️ いまの `variantWork` は `texts` を比べていない（段2は `sameOutsideHoles` で守られていたので漏れなかった）。段4a の道では必ず比べる
  - 比べるのは読んだ結果（行の字面ではなく）。`[BGM]` の前後の空白などの書き癖で止めないため。読んだ結果が同じなら、焼いた絵・素材は同じ
- 違う枚があれば開かず、**違う枚を全部まとめて**理由を出す（1つずつ直させない）:
  「3枚目: 絵の行が見本と違います」「5枚目: 画面の文字（[Text]）が違います——その枚の画面の文字は、作り手向けの道で」「枚の数が見本（8枚）と違います（9枚）」
- 変えてよいもの: 語り（黄色かどうかを問わない）・自由な合図（`> `）・制作メモ・枚の題（`[Slide N]` のあと。語り手の画面にだけ出る）・
  作品の題（`# `。聞き手の画面にも出る）
  - 作品の題が変わると、素材の id（`videoId(work.title, …)`）も変わる。見本の素材は聞き手もサイトから取るので害は無いが、
    聞き手の端末に残した分が使い回されない。**id の計算には見本の題を使い続ける**（画面に出す題だけ替える）を推す
- 画面に出す作品: 見本の `work.json` の、題・各枚の題・`notes` だけを貼った台本のものに替えたもの（`variantWork` を広げる）
- 語りは聞き手へ送らない（いまの保証のまま。段4a の台本でも welcome に notes が入らないことをデータで確かめる）

### 見本の見分け方（Based on の行）

## 1. 段1 見本を玄関から1押しで開く

### 1.1 置き方（第一案: ばらしてエンディング動画を作り直す）

- 静的ファイルは1ファイル 25MiB まで（依頼のとおり）。上演に要るファイルだけを `player/samples/<slug>/<lang>/<版>/…` に置く。
  25MB を超えるのは `videos/ending.mp4`（63.0MB）だけ。
- **エンディング動画は 720p・H.264 の2パスで 22MB 前後に作り直す**。式: 映像のビットレート ≒ 22MB × 8 ÷ 秒数 − 音声（96kbps）。
  約2分半なら映像は約1.0Mbps。絵が動くアニメなので 720p ならこのビットレートで足りる見込み（実際に見て決める）。
  `-movflags +faststart` を付ける（頭から読みながら流せる）。作り直しの打ち方は道具（`ladder/ending-video/` の隣か `tools/`）に残す
- `sounds/bgm.mp3`（11.2MB）は上限の内だが、最初に取る曲としては重い。128kbps に作り直すと約4〜5MB（任意。大きさそろえ §4 は曲を変えないので影響なし）
- 版を道に入れる（`…/1/…`）。中身を変えたら版を上げる → `_headers` に `Cache-Control: immutable` を書ける。
  修正票・段2の変えた版が「どの版の見本を元にしたか」も、この番号で言える（§3）
- `_headers` の CSP は同じ置き場（`'self'`）なので変えなくてよい。
- 第二案（別の置き場。R2 など）は、CSP の `img-src`・`media-src`・`connect-src` に置き場を足すことになる。25MB に収まるあいだは要らない

### 1.2 素材を git に入れずにサイトへ載せる

- 見本ごとに**目録**（`examples/<slug>/<lang>/site.json`）を git に置く: ファイルのパス・大きさ・SHA-256・取ってくる URL、BGM の測った大きさ（LUFS）。
  素材そのものは公開用リポジトリの Releases に置く（今の見本の zip とは別の、サイト用の資産。作り直した軽いエンディング動画はここにだけある）
- 配る直前に、Node の標準だけで書いた取り込み（`scripts/fetch-samples.mjs` のような1本）が目録どおりに取ってきて、SHA-256 を確かめて `player/samples/` に置く。
  合わなければ配らずに止まる
  - 公開用: `.github/workflows/ci.yml` の deploy の `wrangler deploy` の前に1行
  - 開発用の箱: Workers Builds の「ビルドのコマンド」に同じ1行（**ダッシュボードの設定なので持ち主の作業**。いまビルドのコマンドが空かどうかも見てほしい）
- **目録が選び、Releases は置き場にすぎない**。新しい資産を先に Releases へ上げても、公開用の目録が変わるまで本番は変わらない
  （「開発用で確かめてから公開用へ」を崩さない）。Releases に上げる中身は、すでに公開している見本の素材（CC0 など）の作り直しだけ
- ⚠️ 2本目の見本（around-the-same-fire）はまだ公開していない。その素材を公開用の Releases に上げると、それで公開になる。
  公開すると決めるまでは、手元の `wrangler dev` で確かめる（開発用の箱には載せない）
- `player/samples/` は `.gitignore` に入れる

### 1.3 中継費: 見本は聞き手がサイトから直接取る

- いまは語り手が絵・音・動画を DataChannel で送る（別々の家どうしなら TURN を通る＝中継費）。見本なら、聞き手は同じ URL から取れる
- welcome の素材の一覧に、**サイトから開いた見本のときだけ**、サイトの中の道（`samples/…/01.jpg`）を付ける。聞き手はそれを `fetch` して、
  **いまの保存（OPFS／IndexedDB）にそのまま入れる** → 再生・同期・入り直しのコードは変えない。取れなければ、いまの「語り手から送る」に戻る
- 道を付けるかどうかは**読み込んだ場所で決める**（work.json の中身では決めない）。フォルダから開いた作品は、いまと同じく何も付けない。

- **黄色だけを推す**。黄色でない語りは、見本の作り手が出典で確かめた科学の話（スムージーの holes.md「言いすぎを直した流れ」）。
  そこを誰でも変えられると、確かめた言い方が崩れても気づく道が無い。全部を変えたい人は段4（AI と作る）か作り手向けの道へ、1行で案内する
- 名前は「替えてよい所（黄色）」。入口のボタンは「語りを変えてみる」。作り手向けの「直す・修正票」の名前は使わない

### 3.3 画面

- 上演の画面の練習中（受付を開いていないとき）だけ。「家族の端末をつなぐ」を押したら閉じる（いまの `editCtx` の `roomOpen` と同じ扱い）
- 出すのはその枚の黄色い段落の欄だけ。`~ ` は見せない（道具が保つ。行ごとに付け直す）。改行はそのまま
- 欄ごとに「見本の文に戻す」、全体に1つ「全部を戻す」
- 語りは聞き手へ送らない（いまの保証のまま。貼った台本・変えた台本でも welcome に notes が入らないことをデータで確かめるテストを足す）

### 3.4 残すもの: script.md

- 変えた版は、見本の script.md の黄色い段落を差し替えたもの。見出しの自由な行（§2.1。語り手の画面にも出ない）に次を自動で入れる:
  - `> Based on: <見本の題> (<slug>/<lang>, 版 N) — Digital Kamishibai, by Fast Focus Technologies, CC BY 4.0, <URL>`
  - `> Changed: 穴1（1枚目・4枚目・5枚目の語り）` のように、変えた穴
- 開き直すと（玄関に貼る・ファイルを開く）、`Based on` の見本の素材をサイトから取り、台本は貼ったものを B3 の芯で読む
- ブラウザに残す鍵は修正票（`dk-corrections:<題>`）と分ける: `dk-variant:<slug>:<lang>:<id>`。題では引かない（同じ題を貼り直したとき、上書きか別に残すかを聞ける）

### 3.5 残し方（段1〜段4共通）——「ブラウザに残すが、黙らない」

依頼の場面の表に賛成。足すこと・違うこと:

- **知らせの順位**（同時に1つまで）: 版が変わりました ＞ その場で保存（変えた直後） ＞ 直してあります ＞ 残っています
- **プライベートブラウズは見分けられない**（Safari・Chrome とも、確かな方法が無い）。だから「残っています」とは言い切らない言い方を常に使う:
  「この端末のこのブラウザに置きました。ほかの端末で語るとき・消えて困るときは、ファイルに保存してください」＋保存のボタン
- `navigator.storage.persist()` は保存のボタンのあとにだけ呼ぶ（Firefox は許可の窓が出る）。⚠️ いまは `store.js:30` の `freeSpace()` が、
  聞き手の動画の受け取りで呼んでいる。聞き手の端末でも Firefox なら窓が出るはずなので、ここも一緒に見る
- 版が変わった: 変えた段落の元の文（Before）が新しい版の同じ枚に無いとき。変えた版は消さず「見本が新しくなりました。変えた語りはそのまま残っています。合わせて見てください」
- 写真（段4以降）は IndexedDB。容量と Safari の7日の消去がいちばん効くので、写真を入れたら必ず「ファイルに保存（zip）」を勧める
- フォルダから開いた作り手は、いまのまま（修正票。書き戻すのは AI か作り手）

## 4. 段3 「AI に相談」

### 4.1 枚 → 穴の対応: 台本の印に番号を付ける（`~1 `）

依頼の推し（holes.md の表の「場所」を決まった形に）と違う案。理由:

- 印はすでに段落ごとに付いている——必要な細かさ（火の穴3「14枚目の最後の段落」）がそのままある。表の「場所」で段落を言うと、
  「最後の段落」「2つ目の段落」の書き方を決めることになり、台本を直すたびにずれる
- 1枚に2つの穴が乗る（スムージーの4・5枚目は穴1と穴2）。表だけでは、その枚の黄色い段落がどちらの穴かを言えない
- 台本が唯一の元（§1 の考え方）。work.json の notes は `~` を残す決まりなので（§3.2）、**work.json の形を変えずに**プレイヤーまで届く

形: 行頭の `~N `（N は 1〜99、半角）。番号の無い `~ ` は今までどおり（黄色・段3は出さない）。
仕様の変更: §2.3（いまは「`~` のあとに空白が無い」は普通の語り＋警告）・§3.2・§5。ビルダーとプレイヤーの印の外し方も。
holes.md の「場所」の列は人が読むために残し、「印の番号がある枚 ＝ 表の場所」をテストで確かめる。

**決めること**: `~1 ` にするか、依頼どおり表の「場所」にするか。

### 4.2 プロンプトと帰り道

- 単位は穴1つ。中身: その穴がかかる枚の語りを全部（黄色でない所も、流れを読ませるために「変えない所」として）・holes.md のその穴の節・約束事
  （答えは語りの文だけ、改行を保つ、短い行、枚ごとに `[Slide N]` の見出しで返す、1つのコードブロックで）
- **「語る人自身の話」の穴（スムージー穴1・火の穴1）は、AI に書かせず、先に問いを出させる**。チャット AI に「理由を書いて」と頼むと、
  それらしい身の上話を作ってしまう。holes.md の「自分の話を見つける問い」を2〜3個聞いてから、本人の言葉で整える指示にする
- 頭に「家族の名前や写真は、AI に渡さなくてかまいません」
- 帰り: 答えを1つの欄に貼る → `[Slide N]` で分けて各欄へ入れる（入れたあと語り手が見て直せる）。分けられなければ「1つずつ貼ってください」と言い、枚ごとの欄に貼れるようにする
- 出す場所: 段2の欄の横の小さなリンク（「AI に相談（プロンプトをコピー）」）。番号付きの黄色い段落にだけ。上演中の画面には出さない

## 5. 段4 AI と作る

### 5.1 B3（プレイヤーが script.md を読む）に賛成

- 貼った台本だけ script.md を読む。フォルダから開いたら work.json（いまのまま）
- 最初の版の範囲: 語り・BGM・効果音・絵・リンクの動画。`[Text]`・素材の読み替え・エンディング動画の席は「作り手向けの道へ」
- 全角の印: 貼った台本（段3の帰りも）では、行頭の `～ `・`〜 ` を数えて「黄色い所の印が全角になっています。直しますか」と**1押しで直せる**ようにする（黙って直さない）

### 5.2 段4a（B3 の芯のあと、すぐ）

- 条件: 枚の数が見本と同じ、**各枚の `[Picture]`・`[Text]`・`[BGM…]`・`[Sound]`・`[Video]` の行が見本と一字も違わない**。
  このとき見本の焼いた絵（`pictures/_built/`）をそのまま使える。`[Text]` だけ違う枚は「その枚の画面の文字は、作り手向けの道で」
- これでよいと思う。語りはカレーで絵はスムージー、のような食い違いは起きるが、次の「絵の無い枚の板」「ポンチ絵」につながる

### 5.3 プロンプト（見本を元に／ゼロから × ja／en）

- skill を入れずに通る短い指示書＋見本の holes.md・script.md（＋plan.md）。最後に script.md を1つのコードブロックで、`[Slide N]` などの英語は訳さない、行頭の `~` は半角
- ⚠️ 火の見本は holes.md＋script.md＋plan.md で約1,050行（日本語）。無料の枠のチャット AI では1回に貼れない長さかもしれない。
  plan.md（絵のプロンプト）を抜いた版にするか、「ファイルとして添付」にする（実際に貼って確かめる）
- skill を入れた人・Claude Code の人には、いまの道（README の該当箇所）へ1行

### 5.4 絵の上の文字（最初の版では使わない。そのあとの道の比べ）

| 道 | iPad Safari | 描く手 | 手間・危うさ |
|---|---|---|---|
| (a) canvas 用に書き直す | 動く | **2つになる**（overlay-dom.js と canvas）。下書きと聞き手の絵がずれる元 | 日本語の行の折り返し・禁則を自前で。大きい |
| (b) SVG の foreignObject に包んで canvas へ | ⚠️ Safari は foreignObject を描いた canvas を書き出せない（汚染される）ことが知られている。要実験 | 1つ | 字は SVG の中に埋め込まないと効かない |
| **(c) 焼かずに聞き手の側で描く（推し）** | 動く（ただの DOM） | 1つ（overlay-dom.js） | 仕様 §3.2 を変える。録画（`recorder.js`）でも描く |

- (c) で聞き手へ送るのは「画面に出す文字と枠」だけ（notes は今までどおり送らない）。いまの `overlays` は語り手だけのもの、という決まりは残し、
  **聞き手へ送ってよいもの**として別の名前で定義する（中身は聞き手の画面に見える文字そのものなので、新しく漏れるものは無い）
- 字の手当て（どの道でも要る）: いまは `ja` なら Meiryo だけで、iPad では別の字になり幅が変わる。
  **OFL の日本語の字（Noto Sans JP など）を unicode-range で分けてサイトに置き**、描くときはこの字を使う（全端末で同じ幅）。
  CSP は `font-src` が `default-src 'self'` に落ちるので、サイトに置けば変えなくてよい。いまの作品（Meiryo で配置を決めたもの）はそのまま
- **決めること**: (c) で進めるか。字をサイトに置くか

### 5.5 絵の無い枚

- 題と枚番号の板をブラウザの canvas で作る（字は少なく、中央に1行。§5.4 の字の問題は小さい）。聞き手へは JPEG で送る
- ポンチ絵（SVG）: ⚠️ 組み込むかは持ち主が決める。組み込む場合の案:
  - 約束事（「ポンチ絵（下書き）」の印・生成りの紙・破線の枠・線の揺らし・上下の文字の帯）はプレイヤーの側の SVG が持ち、AI は中身だけ
  - `<img>` で読む（blob URL・`image/svg+xml`）。DOM に差し込まない。`<svg` で始まるか・大きさの上限（例 200KB）を見る
  - 聞き手へは canvas で JPEG にして送る。⚠️ Safari で foreignObject の無い SVG を canvas に描いて書き出せるかは iPad で確かめる
  - 字は「短く・大きめ・中央そろえ・sans-serif だけ」を指示書に。登場人物の描き方は最初に1回決めて、以後の枚に渡す
